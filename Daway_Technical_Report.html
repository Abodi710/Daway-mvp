تقرير تدقيق تقني لمشروع داواي

بناء على تخطيط الملفات، ملف package.json، ومخطط قاعدة البيانات في server.cjs.

1. بنية المستودع (العناصر الرئيسية)

daway-prod/                ← الواجهة الأمامية + الخلفية للإنتاج (Vite/React + Node)
 ├─ src/                    ← مكونات React (لوحات القيادة، النوافذ، المساعدات)
 ├─ public/                 ← أصول ثابتة
 ├─ dist/                   ← المخرجات المبنية
 ├─ backups/                ← نُسخ احتياطية أُنتجت تلقائياً لـ SQLite
 ├─ server.cjs              ← واجهة برمجة تطبيقات Express (قابلة للتشغيل مع SQLite)
 ├─ package.json            ← تبعيات Node/Vite والنصوص
 └─ vite.config.js          ← ضبط Vite + React + Tailwind

daway-mvp/                 ← نسخة سابقة/مُبسّطة (JavaScript عادي، server.js)
 ├─ js/                     ← الواجهة الأمامية بـ JavaScript عادي
 └─ server.js               ← واجهة برمجة تطبيقات Express بسيطة

المجلد الجذر/                ← ملفات القفل

2. المكدس التكنولوجي وهندسة النظام

  • الواجهة الأمامية
    • الإطار: React 19 (عبر Vite)
    • التنسيق: Tailwind CSS 4 (عبر @tailwindcss/vite)
    • الإدارة الحالة: React useState/useEffect (بدون مكتبة خارجية)
    • الاتصال: غلاف مخصّص api.js حول fetch
    • البناء: أوامر vite dev | build | preview
  • الخلفية
    • وقت التشغيل: Node.js (Express 5)
    • نمط واجهة برمجة التطبيقات: REST (JSON)
    • المصادقة: JWT (jsonwebtoken) + bcryptjs لتشفير كلمات المرور
    • الوسيط الوسيط: cors, helmet, compression, express-rate-limit
    • قاعدة البيانات: SQLite 3 (الوحدة sqlite3) – قائمة على الملف، متوافقة مع ACID
    • النصوص: node server.cjs (تبدأ الخادم وتزرع بيانات تجريبية)
  • قاعدة البيانات (مقتطفة من server.cjs)
    • مستخدمون (users) – id, pharmacy_name, email (unique), password_hash, role, owner_id, timestamps
    • صيدليات (pharmacies) – id, owner_id (FK → users), name, license_number, address
    • أدوية (medicines) – id, user_id, name, quantity, batch_number, expire_date, price, supplier_id, category, barcode, cost_price
    • مخزون الأدوية (medicine_inventory) – id, pharmacy_id (FK), medicine_id (FK), stock_quantity, price
    • موردون ((include remaining tables)

4. حالة التنفيذ الحالي (ما تم بناؤه مقابل ما يفتقد)

المجالما تم بناؤهما غالبًا ما يفتقد/ثغرات (مقارنة بتطبيقات المؤسسات)
ال CRUD الأساسيالمستخدمون، الأدوية، الطلبات، الموظفين، الموردون، التسجيلات-
المصادقةتسجيل الدخول باستخدام JWT، تشفير كلمة المرور بـ bcrypt، فحص الأدوارلا توجد رموز تجديد دورية؛ لا تأكيد عبر البريد الإلكتروني أو إعادة تعيين كلمة مرور؛ لا مصادقة ثنائية أو تسجيل دخول اجتماعي.
الإذنMiddleware مبني على الأدوار؛ إخفاء أزرار الحذف/التحرير للموظفين في الواجهةلا توجد صلاحيات دقيقة (مثلاً “يمكن حذف طلبات خاصة بي فقط”)؛ لا توجد ضوابط مبنية على السمات (ABAC).
تحقق من صحة البياناتفحوصات يدوية في معالجات الطرقلا توجد أداة تحقق من صحة السيرفر (Joi/Zod) → خطر عدم اتساق الأحمال؛ عدم وجود تنقية داخلية تتجاوز التحقق من الحضور.
معالجة الأخطاءtry/catch → إرجاع 500 مع رسالة؛ أضيف console.error للتشخيصلا وجود لخدمة سجل مركزي (مثلاً Winston، Sentry)؛ عدم وجود معرّفات ارتباط لتتبع الطلب.
الأداءSQLite مع مفاتيح أولية/أجنبية (فهرسة ضمنية)؛ gzip؛ تقيد معدل الطلباتطبقة قراءة/ذاكرة مؤقتة غير موجودة (Redis) للتقارير الثقيلة؛ لا وجود لتخزين على مستوى الاستعلام (مثل عروض مادية للالخصاص); لا وجود لتقسيم القوائم الكبيرة (الأدوية، الطلبات).
المرصادسجلات وحدة التحكم الأساسية، إشعارات النسخ الاحتياطيلا يوجد سجل منظم (JSON)؛ لا نقطة نهاية لمقاييس (Prometheus)؛ لا فحص صحة يتجاوز /status.
DevOpsنص النسخ الاحتياطي، بناء Vite، تشغيل Nodeلا يوجد ملف Docker / docker‑compose؛ لا مسار CI/CD (GitHub Actions)؛ لا بنية تحتية كرمز (Terraform).
الاختبارلا توجد اختبارات مكتشفةلا توجد اختبارات وحدة/تكامل (Jest, Vitest)؛ لا توجد اختبارات من طرف إلى طرف (Cypress/Playwright)؛ لا فرض لتغطية الاختبار.
توثيق APIلا يوجدلا توجد مواصفة OpenAPI/Swagger؛ لا توجد وثائق تفاعلية (Swagger UI).
هياكل الواجهة الأماميةمستوى المكونات، حالات محلية، هوائيات مخصّصة ضمنيةلا يوجد مدير حالة عالمية (Redux/Zustand) – قد يتسبب ذلك في مشاكل於 التوسع؛ لا يتم تحميل الأجزاء الثقيلة (مثل المخططات) عند الطلب؛ لا توجد مكتبة تحقق من النماذج (react-hook-form / Yup).
الواجهة وتجربة المستخدمصفحات مصممة بـ Tailwind، جداول عرض، نوافذ منبثقة، تنبيهات، رسم بياني خطّيلا يوجد تدقيق للوصولية (ARIA، تنقل لوحة المفاتيح)؛ لا يوجد وضع داكن؛ لا يوجد دوْلة (العربية موجودة لكن لا يتم تكييفها بالكامل).
الأمانHelmet, CORS, تقييد المعدل، أسرار JWT في .env، كلمات المرور مُشفّرةلا توجد إعدادات HttpOnly وSecure لملفات تعريف الارتباط (إن وُجدت)؛ لا توجد حماية من هجمات CSRF؛ لا توجد مسح للاعتماديات (npm audit) في سلسلة التكامل؛ لا يوجد اختبار لتعريض المسارات للأدوار (محاولة موظف accessing مسار مالك).
سلامة البياناتتم تمكين قيود المفاتيح الأجنبية (PRAGMA foreign_keys=ON)لا وجود لآليات ترحيل تلقائية (Knex, Sequelize) – تغييرات المخطط يدويّة؛ لا وجود لتدقيق للمسح أو الحذف اللين؛ لا يوجد تشفير في حالة الاستراحة لـ SQLite (يعتمد على تشفير ملف نظام التشغيل فقط).

5. توصيات الأمان (أولوية)

  1. إدخال دورة تجديد رمزrefresh – تخزين رموزrefresh مشفّرة في قاعدة البيانات وإصدار رموز وصول قصيرة العمر.
  2. إضافة تحقق شامل من الصحة – اعتماد مكتبة مثل Zod أو Joi لأجسام جميع الطلبات وتنظيف السلاسل لتفادي حقن.
  3. تنفيذ رموز CSRF – للاعتماد المستند على ملفات تعريف الارتباط (أو الاعتماد على رأس Authorization: Bearer فقط كما هو معمول به حالياً).
  4. تمكين السجل المنظم (winston/pino) مع معرّفات طلب؛ إرساله إلى خدمة خارجية (ELK, Datadog, إلخ).
  5. إضافة رؤوس أمان تتجاوز Helmet: Content‑Security‑Policy, Referrer‑Policy, Permissions‑Policy.
  6. تشغيل تدقيق للاعتماديات (npm audit, npm outdated) في مسار التكامل المستمر والحفاظ على ملفات القفل محدثة.
  7. النظر في الانتقال إلى PostgreSQL للتوسع متعدد المستخدمين، أمان على مستوى الصفوف، وأدوات أفضل.
  8. فرض HTTPS في الإنتاج (عبر وكيل عكسي – Nginx/Caddy) وتعيين علم Secure على ملفات تعريف الارتباط إذا استُعملت إذا استُخدمت.
  9. تطبيق قفل الحساب بعد N محاولات دخول فاشلة.

6. توصيات الأداء

  1. إضافة التقسيم أو مؤشرات kursor للقوائم الكبيرة مثل /medicines, /orders, /users لتجنب تحميل جداول ضخمة.
  2. تخزين الملخصات المجمّعة (مثل /api/owner/sales/summary) لفترة قصيرة باستخدام ذاكرة مؤقتة (Redis أو ذاكرة داخلية typu LRU) لأنّ الطلب يجمع جداول متعدّدة.
  3. إنشاء فهارس جزئية على أعمدةrea تُستخدم بشكل متكرر في الفلاتر: مثال owner_id, status = 'pending', نطاقات تواريخ الصلاحية.
  4. نقل المهام الثقيلة (تصدير CSV/PDF) إلى عمال خلفية (مثلاً BullMQ) لتحرير سلاسل API.
  5. استخدام مخطط استعلامات SQLite – تشغيل EXPLAIN QUERY PLAN على الاستعلامات البطيئة مع نمو البيانات.
  6. اعتبار تجميع الاتصالات (better‑sqlite3) إذا ارتفعت الحركة المتزامنة.
  7. تمكين HTTP/2 عبر وكيل عكسي لتحسين تعددية الأصول الثابتة.
  8. فحص حجم الحزمة – راجع مخرجات vite build؛ حمّل المخططات الثقيلة (recharts) فقط عند الحاجة.
  9. استخدام ETags و Cache‑Control للأصول الثابتة (Vite فعلاً efectu ذلك في بيئة الإنتاج).
  10. مراقبة حجم قاعدة البيانات – جدولة عملية VACUUM عند حدوث عمليات حذف كثيرة.

7. الخلاصة والخطوات القادمة

مشروع داواي‑MVP/Prod يقدم نموذج عمل وظيفي لإدارة الصيدليات يتضمن:

  • واجهة برمجة تطبيقات REST واعية بالأدوار مدعومة بـ SQLite.
  • تطبيق صفحة واحدة React/Vite مع تنسيق Tailwind.
  • التدفقات الأساسية للأعمال (الوصف، الطلب، المخزون، التوظيف).
  • الميزات المضافة حديثاً: نظام الإنذارات الذكية، تطبيق صارم للتحكم المستند إلى الأدوار، ورسم بياني للمبيعات اليومية.

للتحوّل من نموذج أولي يعمل إلى حل SaaS جاهز للإنتاج، يجب الانتباه إلى المجالات التالية:

  • تصلب الأمان – تجديد رموز الدخول، تحقق من الصحة، تسجيل منسق، رؤوس أمان قوية.
  • المراقبة والموثوقية – سجلات منظمة، مقاييس، التحقق من النسخ الاحتياطي.
  • قابلية التوسع – التقسيم، التخزين المؤقت، احتمال الترحيل إلى قاعدة بيانات أكثر قوة.
  • تجربة المطور – خطوط دمج ونشر مستمر، اختبارات، تبني TypeScript، مواصفات OpenAPI.
  • الامتثال وتجربة المستخدم – إمكانية الوصول، مسارات تدقيق، دوْلة، عرض كثيف للبيانات.

هذه الخطوات ستوفّر أساساً متيناً لتوسيع الميزات المستقبلية مثل الوصفات الإلكترونية، مطالبات التأمين، شبكة صيدليات متعددة، ولوحات تحليلية متقدمة.
